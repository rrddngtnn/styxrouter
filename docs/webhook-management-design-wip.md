# Webhook management design — blocked, not mounted

Do not mount or enable management until the strict public-only URL guard is fixed and independently tested, including literal and resolved addresses, regardless of private-provider overrides. Transport remains responsible for DNS resolution, address pinning, and redirect rejection at every delivery. The validator in `server/webhookManagementValidation.ts` requires a caller-supplied guard and is not a security boundary by itself.

Proposed API: authenticated management-session-only CRUD under `/api/webhooks`; use the existing `requireAuth` middleware and its same-origin checks for unsafe methods. Include `Cache-Control: no-store`, generic validation/storage errors, bounded inputs, and explicit response projections. Never return signing secrets, encrypted values, metadata, or destination URLs with credentials; consider destination paths and query strings sensitive in logs and audit records. Accept only explicit event names in `WEBHOOK_EVENT_VALUES`, never `*`. Create should generate a random signing secret server-side; the API contract for communicating it to the receiver must be decided before implementation. Do not silently expose it on ordinary reads.

Persist the secret encrypted with a configured and current storage key; fail closed when encryption is unavailable or ciphertext cannot be verified. The existing encryption helper may return plaintext on failure or accept a prefixed value without encryption, so test the result, not just the configuration. Do not accept caller-provided ciphertext. Secret rotation, if exposed, must be explicit and atomic.

Use database transactions for create/update/delete and any corresponding audit record, with errors causing rollback and with durable persistence under each supported adapter. Exercise concurrent mutations and rollback. Avoid read-modify-write lost updates. Ensure existing legacy rows are not unintentionally overwritten or exposed.

Management remains unmounted. An experimental separate provisioning application and storage primitive return a generated secret only in the initial authenticated no-store response; they insert the encrypted secret, idempotency record and sanitized audit in one immediate transaction. A retry with the same idempotency key and identical input returns the ID without the secret; changed input conflicts. If the initial response is lost, the secret cannot be retrieved: an operator must delete/recreate or rotate via a separately designed and audited recovery operation. Do not blindly retry with a new key, which creates a duplicate. The request-key tombstone must survive webhook deletion, and key rotation, restore and backup behavior require a documented durable policy before enabling. The experimental migration `185_webhook_provisioning.sql` is present but pending deployment; it has been applied only to isolated synthetic test databases here, not production. It creates the durable request and audit prerequisites without changing existing webhooks. Deployment requires a backup, migration review and the normal controlled rollout; do not mount or restart for this prototype.

Rotation requires the exact opaque quoted `version` returned by the successful create or rotation response in `If-Match`. The immediate transaction checks the version against the stored ciphertext and performs a conditional update, idempotency insert and sanitized audit insert atomically. Concurrent distinct keys with the same expected version yield one success and one conflict; sequential rotations using a newly obtained version can still supersede an earlier secret. Same-key retry must retain the same version and returns only the ID, never the secret; changed version conflicts. Failed conflicts do not consume the key. If a success response is lost, a replay cannot recover its secret or version; an administrative recovery/read design is still required. Do not blindly issue another rotation with a stale version. The version is not a secret, but no version-recovery endpoint exists in this prototype.

Storage-key rotation is **not supported** for this candidate: changing `STORAGE_ENCRYPTION_KEY` changes both ciphertext decryption and idempotency fingerprints; no atomic rekey of all encrypted application fields and tombstones exists. Do not change the key or enable the candidate on the assumption that webhook signing-secret rotation rekeys storage. A signing-secret rotation now rejects plaintext, malformed or unauthenticatable existing secrets rather than overwriting them; it does not validate the entire database or prevent new creates under a wrong key. Retain the exact storage key securely, separately from each consistent encrypted SQLite backup, for the complete backup retention period. Restore only offline into an isolated environment first, with the matching key, and verify authenticated decryption and ledger/audit consistency before any controlled recovery. Restoring an older backup rolls back secrets, idempotency tombstones and audits: receiver state and requests after the snapshot require explicit reconciliation; never blindly replay them. Backup files and keys remain sensitive. The synthetic Bun SQLite backup test is not evidence that the production restore mechanism or other adapters are safe; migration 185 and adapter durability remain deployment blockers.

The unmounted app performs strict literal validation and bounded public-only DNS resolution before persistence; this is not a substitute for delivery-time resolution and pinning. Two independent HTTP processes sharing a synthetic SQLite database exercise idempotent create/rotate races, authentication, cross-origin rejection and redaction. Mounting remains blocked pending independent security review, trusted proxy/origin policy, durable adapter and migration policies, and complete management design. Existing `createManagedWebhook` still discards its generated secret. Legacy `db/webhooks.ts` returns secrets to callers, so management reads must use explicit secret-free projections and leave legacy records unchanged.

The custom delivery path now decrypts stored ciphertext only at dispatch and fails closed on decryption errors; legacy plaintext keys retain their existing HMAC behavior. Focused tests cover HMAC and pinned SSRF transport, but do not establish end-to-end management security or audit atomicity. Do not mount until those requirements are independently tested across supported adapters.

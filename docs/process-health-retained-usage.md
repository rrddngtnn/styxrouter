# Process health retained usage

`GET /api/process-health/dispatch` retains its existing response shape and `source: "retained_usage_history"`. This is retained usage data, not proof that an upstream dispatch occurred, a complete request ledger, or a provider eligibility signal.

`asOf` is the UTC snapshot time. Only records with valid SQLite-parsable timestamps at or before `asOf`, nonempty providers, and success 0 or 1 are included. The `hour` and `day` request and failure counts use inclusive trailing one-hour and 24-hour windows ending at `asOf`; future and invalid timestamps are excluded. Providers with only older observations remain visible with zero window counts. `lastSuccessAt` and `lastFailureAt` represent the latest retained observation of each outcome across all retained history, or null. They are normalized to UTC ISO 8601 with milliseconds, rather than preserving an imported offset spelling. Field names and types remain unchanged, but consumers comparing raw timestamp strings should compare instants instead.

The first query scans retained history to preserve all-history latest observations. A process-local snapshot is reused for at most one second from its original `asOf`; the response retains that original `asOf`. SQLite `data_version` invalidates it after commits from other connections, and `total_changes()` invalidates it after writes on the same connection. These checks apply to the entire database, so unrelated writes also invalidate it. The sql.js driver and drivers without exposed transaction state bypass caching, as do reads inside transactions. A write concurrent with a read may be reflected on the next request, as with ordinary SQLite snapshot reads.

This is not a constant-time probe: cold reads and reads after any database write still scan all retained history. Under continuous writes the cache may provide little benefit; limit usage-history retention appropriately for the installation. No data is deleted or migrated by this endpoint.

# Combo tag dispatch consistency: known race

## Current semantics

For a tagged combo request, routing filters candidates and then `handleSingleModelChat` re-reads the selected connection's active flag and tags from SQLite. A mismatch or invalid read fails closed at that point. This is **snapshot eligibility**, not a guarantee that the connection remains tagged through outbound dispatch. A committed retag or deactivation after that read can precede the upstream request; token refresh, proxy resolution and other asynchronous work follow the read. In-flight requests are not cancelled by tag changes. Do not use account tags as an immediate credential-revocation or authorization boundary.

`tests/combo-tag-toctou-two-process-regression.test.ts` exercises a retag before the durable read and expects no send. `tests/combo-tag-post-revalidation-race-observation.test.ts` documents the residual gap: at proxy resolution (after the read), a child commits a retag before dispatch; the mocked upstream still receives one request. This is an observation test, not a safety regression; change its expectation if a stronger contract is implemented.

## Design choices and blocker

A revision checked at selection or again immediately before calling fetch reduces the window but cannot close it: a different process can commit after the final check and before bytes are sent. SQLite transactions must not be held across network work. A process-local mutex cannot synchronize other servers, and a time-expiring lease alone cannot stop a paused holder from sending after expiry. A fencing number only works if the actual downstream transport or provider rejects stale fences; existing external providers do not provide that guarantee.

A feasible cooperative **admission** contract is different from strict send-time revocation: atomically validate active/tags and register an independent per-connection dispatch admission under a short SQLite write transaction. Retag/deactivation writers must coordinate with admissions and define whether they wait, fail, or commit while admitted requests proceed. The admission commit becomes the linearization point: requests admitted before a mutation may still send after it; requests admitted after must observe the new state. Such a design needs per-attempt ownership, release on all error/abort paths, crash recovery, retries and streaming lifecycle semantics, bounded waiting, all relevant writer and deletion/restore paths, multi-process tests, migration coordination, and draining old binaries. Expiring a lease cannot safely permit strict revocation of a paused process unless the sender is independently prevented from using it; blocking forever instead is a liveness failure. Direct SQL and old binaries must be fenced or explicitly excluded from the guarantee. Existing exclusive/occupancy leases should not be assumed to provide these semantics.

A stronger promise that **no outbound send occurs after retag commit** requires coordination through the actual irreversible send boundary, including all executors, retries and provider-specific refresh requests. A centralized egress coordinator with a controlled transport could serialize mutation acknowledgement against actual send initiation, but cannot revoke bytes already sent or make the provider undo accepted work. It needs explicit handling for crashes, streaming, network buffering, and noncooperative writers. There is no established transport-wide fencing or agreed revocation contract here, so implementing a scoped lease or revision alone would falsely claim safety. No implementation or migration was made.

# Imported OAuth refresh remains disabled

The `importedRefreshClaim` module is an **unwired experimental primitive**, not an enabled refresh implementation. Existing imported-credential blocks remain in place. Do not remove them or call these functions from a refresh path without completing and reviewing the work below.

The primitive uses an immediate SQLite transaction to insert a non-expiring random operation claim in `key_value`, keyed by an HMAC of provider and refresh token using the configured storage secret. Successful completion checks ownership and the original encrypted refresh token, round-trip encrypts both new tokens, and updates the pair, inserts a secret-free config audit record, inserts a durable used-token HMAC marker in `imported_refresh_used_v1`, and removes the claim in one transaction. An error rolls the transaction back; there is no lease timeout or automatic release. Tests use two independent Bun processes sharing WAL/FULL SQLite and the default CBCN exchange with its fetch redirected to a local rotating-token mock. Success makes one request and rejects concurrent and stale callers; SIGKILL after claim, after response, and after the update inside the persistence transaction retains the claim and old pair. An audit-rejecting trigger verifies rollback. These tests do not prove power-loss durability or other SQLite adapters; the synchronous pragma check alone does not establish those guarantees.

## Current CBCN status and reauthentication blocker

The ordinary CBCN refresh path now uses `codebuddyRefreshFence`: it requires an explicit database and connection ID, claims the token digest before exchange, and commits the encrypted rotation and audit before publishing. Raw and generic entry points without the authoritative context are denied. Marked imported pairs remain blocked from production refresh; `importedRefreshOrchestrator` is still experimental. The isolated tests `codebuddy-refresh-boundary-regression`, `cbcn-fenced-route-regression`, and `import-refresh-orchestrator-two-process-regression` pass (11 tests). The last exercises an experimental imported orchestrator with a synthetic upstream, not the complete production reauthentication lifecycle.

**Recovery is not implemented.** A claim held after an ambiguous refresh is intentionally permanent, including if the connection is deleted or recreated. Reusing the old refresh token remains denied; do not delete a claim, expire it by time, rotate the storage key, or restore an older database as a recovery workaround. Snapshot rollback and key changes can invalidate the fence and need separate operator safeguards. A fresh authorization may create a separate connection, but this has not been verified as a safe replacement workflow and does not repair the existing connection.

The existing authorization paths do not establish a trustworthy, connection-scoped fresh-authorization handoff. In `server/styx.ts`, `toOauthKey('codebuddy-cn')` yields `codebuddyCn`, while the OAuth registry key is `codebuddy-cn`; the Hono init/poll lookup therefore does not resolve this provider. Its generic poll also accepts a state absent from `deviceFlows`, does not bind the flow to a provider or target connection, and always calls `createProviderConnection`; the legacy POST poll accepts a caller-supplied device code and does not bind it to a server-created authorization or atomically replace the specified CBCN row. CBCN's poll response maps tokens but supplies no verified account identity. Neither path currently supplies sufficient provenance or identity to safely distinguish fresh authorization for the intended account from replay or a different account. A safe implementation needs a provider- and target-bound one-use server-side flow, a verified identity or explicit reviewed account-binding contract, atomic encrypted pair replacement and audit, and continued retention of the old digest fence. It must reject old or previously claimed/used replacement tokens, race against refresh/delete, and be demonstrated by a two-process crash-then-reauthorize integration with synthetic credentials. No such integration proof is currently present.

## Separate fresh connection: investigation and remaining proof

A separate new connection avoids asserting that the newly authorized account is the same as the uncertain old one. It is not a replacement or account recovery: the old row, claim and used-token markers must remain untouched, and the operator must not be told that either identity matches or that the old token was revoked. The provider's `pollToken` maps access and refresh tokens but provides no verified identity, and a fresh device state by itself does not establish that the resulting refresh token is new or that authorizing it cannot invalidate an earlier session. No provider contract proving those properties was found in the inspected implementation.

The current Hono flow cannot serve as the trusted handoff: it does not resolve the CBCN registry key, it accepts unknown state, and its in-memory state is neither provider-bound nor one-use across processes. The legacy POST poll accepts a caller-supplied device code. Simply fixing the lookup, using the caller's state, or comparing an unverified account identifier would not establish provenance. No new connection implementation has been enabled.

A candidate must initiate CBCN device authorization server-side, associate a high-entropy opaque handle with the exact server-obtained provider state and authenticated operator session, and let only a server-side poll use that state. A durable cross-process single-consumer transition must reject unknown, expired, wrong-session/provider, duplicate and concurrent polls; failures and crashes after a potentially consuming poll must fail closed, not retry automatically. The callback result must never be accepted from the client. Persist a separate new row and a sanitized audit atomically with round-trip encryption, after checking the fresh refresh token against existing CBCN rows and the same durable claimed/used digest fence in the transaction. Do not modify or unfreeze the uncertain row. All entry points, storage backends, cache behavior and backup/restore/key-change risks need review; an in-memory lock is insufficient.

Before implementation is considered safe, demonstrate the provider's actual device authorization and token lifecycle contract, particularly whether issuance may reuse a refresh token or invalidate another session. Synthetic tests alone cannot prove upstream semantics. In isolated synthetic tests, exercise server-issued state binding and server polling, wrong session/provider, arbitrary state, expiration, replay, duplicate/concurrent consumers across two processes, ambiguous network and crash boundaries, token collision with frozen/used claims and other rows, encrypted atomic insert/audit rollback, and old-connection/claim preservation. Include a crash-then-fresh-authorization integration that verifies old stale refresh remains denied and the new row can refresh safely; test actual dispatch paths and peer caches. Until those properties are established, this is a design candidate, not a supported recovery method.

The existing three isolated fence suites were rerun with synthetic credentials: 11 tests passed, including two-process crash/claim cases. They do not exercise fresh authorization and do not establish upstream issuance semantics. No production database, service restart, or commit was used.

## Earlier CBCN review (historical findings)

The following notes record the earlier experimental review. References to unfenced ordinary/raw/generic exchanges and failing raw/generic tests describe the state at that review, not the current fence described above.

- Direct provider exchange (`open-sse/services/tokenRefresh/providers/codebuddyCn.ts`) accepts a raw token and has no claim context. The experimental orchestrator now requires an explicit nonempty refresh token in the response rather than accepting the legacy fallback; a two-process test confirms an ambiguous response retains the claim. The ordinary raw-token helper still permits the fallback and bypasses claims. Establish the upstream rotation contract and fence every reachable direct exchange before enabling.
- Dispatch's generic `refreshAccessToken` rejects marked imports; `getAccessToken` and the executor refresh route must be integrated through the same durable claim rather than bypassing that guard. The raw CBCN helper cannot distinguish an imported token from an ordinary one. Test proactive and reactive dispatch with stale credentials in separate processes.
- `server/modelSync.ts` currently has a Codex-specific refresh path, not a CBCN refresh integration. Any future CBCN sync path must carry connection identity and use the same claim; the Codex path remains separately blocked for marked imports.
- Quota `refreshAndUpdateCredentials` rejects forced or expired marked imports and otherwise skips their refresh. Token health skips marked imports; admin connection testing also skips them. Integrating dispatch alone would leave these paths inconsistent and does not satisfy the all-path gate.
- `finishImportedRefresh` checks the current key and round-trip encrypts both fields, then updates credentials, inserts a sanitized audit row, and deletes the claim in one immediate transaction. General `updateProviderConnection` independently validates encryption for marked imports but is not the claim-and-audit transaction; callbacks must not publish or overwrite rotated credentials outside it. Its cache invalidation is local, not a demonstrated peer invalidation mechanism.
- Claims and used markers fence the same provider and refresh token across duplicate connection IDs through the orchestrator, including after success. Raw helper calls bypass both. Restored snapshots and key rotation require explicit fencing and recovery semantics; a marker must never be cleared merely because time passed.
- The duplicate two-process regression passes while the first claim is held. The `raw` and `raw-forged-flag` scenarios fail: the second process calls `refreshCodebuddyCnToken` without a database or connection ID, sends a second request and prints `SUCCESS` while the first claim remains held. Reproduced with `PATH="$HOME/.bun/bin:$PATH" bun run server:test tests/import-refresh-orchestrator-two-process-regression.test.ts` (6 passed, 3 failed: raw, raw-forged-flag and generic). The test uses a scratch database and a local synthetic-token server.
- A second bypass exists in the generic `refreshAccessToken("codebuddy-cn", ...)`: it constructs its own HTTP request and trusts caller-provided `providerSpecificData.importedToken`. Fencing only the provider-specific helper would leave that path open. Both exchange mechanisms must converge on a common database-backed entry point before network I/O; a boolean supplied by the caller is not proof of ownership.
- The two-process regression also exercises this generic route with a synthetic CBCN refresh URL injected into the in-memory provider configuration. It sends a second request while the original claim is held; without that injection the current registry lacks a refresh endpoint and returns null, which would be a false-positive fence test. This demonstrates the generic code path is unsafe if an endpoint is configured, not that the default registry currently sends that request.
- Ordinary CBCN OAuth is allowed through the raw helper and generic refresh entry, but neither participates in the experimental claim. A concurrent ordinary refresh can rotate the same token while an imported claim is held, including across processes; caller-provided import markers are not authoritative. This is an unresolved race, not a safe imported-refresh implementation. Non-imported CBCN OAuth cannot safely rely on the current raw helper: it may possess the same refresh token as an imported row. Its connection identity must be resolved against the authoritative database, and its exchange and persistence must participate in the same token-digest claim. The generic callback path currently persists after the exchange and `updateProviderCredentials` can return false; blindly wrapping the HTTP call does not guarantee a durable rotation before publishing. Decide and test the semantics for a missing connection ID and a missing rotated refresh token before changing those paths. Do not treat the temporary denial of every raw call as a completed fix: that breaks legitimate OAuth without providing an integrated replacement.
- The fixture's raw worker constructs a separate SQLite adapter for its scratch database but passes no adapter or ID to the raw function. A common entry point therefore needs explicit authoritative database context or an equivalent trustworthy injection; selecting the process default database from that helper would not fence the fixture's database and can silently protect the wrong store. Crash-held claims and used markers must continue to apply to both imported and non-imported callers; key changes and snapshot restore remain explicit recovery barriers.
- The two-process fixture kills before fetch, after the HTTP response, and inside the write transaction; it does not kill during an in-flight request, test a server-consuming-but-disconnecting response, prove post-commit peer-cache behavior, or prove filesystem/power-loss durability. Audit rollback is separately tested. Production backend coverage and encryption failure for each field at this orchestrator boundary remain required.

## Required before enabling

- Wire **every** proactive, reactive, manual, quota and direct executor refresh path for marked imports through the same persistent claim before any network request. Ensure provider-specific refresh entry points cannot bypass it; avoid any retry after an ambiguous network outcome. Publish results only after committed persistence, and handle every persistence callback and error without leaking credentials.
- Verify effective SQLite durability and backend semantics on all supported native adapters, including journal modes, nested transactions, filesystem and power-loss guarantees. The current synchronous pragma check alone is not sufficient proof of durability. sql.js is rejected. Define backup/restore and duplicate-connection behavior; restoring an older database cannot protect tokens already rotated externally.
- Exercise two independent OS processes against a local HTTP rotating-token mock, including stale caches and both successful and ambiguous responses. Kill processes after claim, during network and during persistence; verify durable claim retention and no second upstream rotation. Test encryption failure on each field, injected transaction failure, rollback, stale owner and concurrent changes.
- Provide an explicit operator reauthentication/replacement workflow. Never clear a claim solely because time elapsed; deleting or replacing the connection must not allow another process holding an old credential to rotate it. Claims currently have no supported recovery UI.
- Cover peer cache invalidation and all import/dedup/edit/delete paths, and validate provider-specific rotated-token and expiry contracts. Historical unmarked Codex imports cannot safely be classified by metadata heuristics; the existing separate operator freeze remains necessary.

Tests use synthetic credentials and the isolated runner, not a live database. No process restart or deployment is part of this change.

# Corrupt API key quota policy recovery

Malformed `allowed_quotas` is treated as unavailable, not as an empty (unrestricted) list. Pool deletion validates all stored quota policies transactionally and rolls back if any is corrupt, even if that key might be unrelated. This is deliberate: malformed data cannot reliably establish whether the key references the deleted pool, and skipping it could later revive a dangling authorization if the pool ID is reused. No automatic rewrite attempts to guess the original permissions.

An authenticated administrator can replace a corrupt policy with the reserved deny-all marker using `PATCH /api/keys/:id` with JSON body `{"allowedQuotas":["__quota_access_revoked__"]}`. The same atomic update also disables the key, including when `isActive: true` is supplied, because some requests have no model for quota validation. This restores parseability without granting access; after recovery the pool deletion can be retried. Reactivation is a separate, explicit admin action. The marker does not resolve to a quota pool. An unrelated name-only PATCH leaves the corrupt policy untouched and does not restore access. The API deliberately does not accept arbitrary quota lists through this recovery field.

This is a local source change; activation requires the coordinated deployment and reserved-ID migration. The code does not repair corruption by itself, and the administrator must identify and recover all corrupt keys blocking a deletion. A corrupt row may also prevent list views that hydrate every key; use the known key ID or an authorized database inspection to locate affected records.
